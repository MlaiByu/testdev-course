## 三、fixture 作用域（你 fixture 口头题的现实版）

| fixture | 作用域 | 为什么 |
|---|---|---|
| `base_url` | session | 常量，整场不变 |
| `api` | session | `requests.Session` 复用 TCP 连接，整场只建一次 |
| `token` | session | 注册+登录有成本，全会话只做一次（订单组共用） |
| `unique_email` | function | 每条用例必须拿新邮箱，否则注册类用例互相撞车 |
| `auth_headers` | function | 字典是可变对象，防止用例 A 改坏用例 B 的 header |

**一句话原则：贵的、不变的 → session；会变的、会被改的 → function。**

顺便回答你欠的那道 fixture 题：`admin_client` 用 session，是因为"登录态"昂贵且全局复用；`draft_post_factory` 用 function，是因为每条用例要造独立的草稿数据、彼此不能看见。这和你这套 `token` vs `unique_email` 是同构的。

## 四、断言四层（失败时一眼定位）

```python
assert r.status_code == 201        # ① 请求层：接口通道通不通
assert body["code"] == 0           # ② 业务层：业务码对不对
assert body["data"]["email"] == ...  # ③ 数据层：字段值对不对
assert "hashed_password" not in body["data"]  # ④ 契约层：敏感字段不泄漏
```

- ① 挂 = 接口/路由/服务问题
- ② 挂 = 业务码与预期不符（先查契约文档）
- ③ 挂 = 数据处理逻辑错（归一化、截断、舍入）
- ④ 挂 = 安全契约被破坏（最严重）

## 五、三条工程规矩（比语法值钱）

1. **用例自给自足**：`test_register_duplicate_email` 内部先注册一次再重发——**不依赖 API01 先跑过**。pytest 默认不保证执行顺序，靠顺序活的用例迟早挂。
2. **参数化代替复制粘贴**：4 个非法密码值 → 1 个函数 + `@pytest.mark.parametrize`，报告里显示 4 条独立用例，失败时精确到哪组数据。
3. **断言具体值，不断言"非空"**：`assert data["email"] == 期望的小写值`；只写 `assert data["email"]` 等于没测。

## 六、命令速查

| 命令 | 用途 |
|---|---|
| `pytest -v` | 看每条用例名和结果 |
| `pytest -k register` | 只跑名字含 register 的 |
| `pytest -x` | 首条失败即停（调试时用） |
| `pytest --tb=short` | 精简报错栈 |

读失败输出顺序：**用例名 → 文件:行号 → 断言表达式 → diff**。
